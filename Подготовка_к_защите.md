# Часть 1. Теория с нуля

## 1.1. Как вообще работает веб

**Клиент-серверная модель.** Браузер (клиент) отправляет **запрос**, сервер возвращает **ответ**. Общаются по протоколу **HTTP**.

**URL** `http://127.0.0.1:8000/detail_product/1/?x=5`:

| Часть | Значение |
|---|---|
| `http` | протокол |
| `127.0.0.1` | адрес сервера. `127.0.0.1` (он же `localhost`) — «этот же компьютер», запрос никуда в сеть не уходит |
| `8000` | порт — номер «двери» на компьютере, за которой слушает программа. 8000 — порт сервера разработки Django по умолчанию |
| `/detail_product/1/` | путь — по нему Django выбирает, какую функцию вызвать |
| `?x=5` | параметры GET-запроса |

**HTTP-запрос** состоит из метода, пути, заголовков (в т.ч. cookie) и тела. **HTTP-ответ** — из кода состояния, заголовков и тела (обычно HTML).

**Методы:**

| | GET | POST |
|---|---|---|
| Назначение | получить данные | отправить данные, изменить что-то на сервере |
| Где данные | в URL (`?a=1`) | в теле запроса |
| Видны в адресной строке | да | нет |
| Можно добавить в закладки, повторить | да | нет (браузер спросит «отправить повторно?») |
| Когда использовать | страницы, поиск | формы, меняющие БД: создание, вход, корзина |
| CSRF-защита в Django | не проверяется | проверяется |

**Коды ответа**, которые встречаются в проекте:

| Код | Смысл | Где в проекте |
|---|---|---|
| 200 | OK | обычная страница |
| 301 | постоянный редирект | `/detail` → `/detail/` (Django сам добавляет слэш) |
| 302 | временный редирект | `redirect(...)` после добавления в корзину, удаления; переброс на логин |
| 403 | запрещено | POST без `{% csrf_token %}` |
| 404 | не найдено | адреса нет в `urls.py` |
| 405 | метод не разрешён | GET на `/add/1` (там `@require_POST`), GET на `/accounts/logout/` |
| 500 | ошибка сервера | исключение в коде, например `/detail_product/9999` |

**HTML** — разметка страницы, **CSS** — оформление, **JavaScript** — поведение в браузере. **Frontend** — то, что исполняется в браузере; **backend** — то, что исполняется на сервере (у нас Python/Django).

**Статический сайт** — готовые HTML-файлы. **Динамический** — HTML собирается на сервере при каждом запросе из шаблона и данных БД (наш случай).

**HTTP не хранит состояние**: каждый запрос независим, сервер «не помнит» прошлый. Чтобы помнить пользователя, используют **cookie** (маленькие данные, которые браузер хранит и прикладывает к каждому запросу) и **сессии** (данные на сервере, а в cookie — только ключ к ним). На этом держатся вход в систему и корзина.

## 1.2. Минимум Python, который нужен для ответов

- **pip** — менеджер пакетов Python: `pip install django`, `pip list`.
- **Модуль** — файл `.py`; **пакет** — папка с `__init__.py`. `from .models import Product` — точка значит «из этой же папки».
- **Класс и наследование:** `class Product(models.Model):` — `Product` получает всё поведение `models.Model` (умение сохраняться в БД и т.д.).
- **`*args, **kwargs`** — «принять любые позиционные (`args` — кортеж) и именованные (`kwargs` — словарь) аргументы». `**form.cleaned_data` при вызове, наоборот, **распаковывает** словарь в именованные аргументы.
- **Словарь** `{'ключ': значение}` — основа контекста шаблона и корзины.
- **Декоратор** `@require_POST` — обёртка над функцией, добавляющая проверку перед её вызовом.
- **«Магические» методы:** `__init__` — конструктор; `__str__` — строковое представление объекта; `__iter__` — делает объект перебираемым в `for`; `__len__` — что вернёт `len(obj)`.
- **`yield`** — функция-генератор: отдаёт значения по одному, а не списком целиком.
- **`Decimal`** — точные десятичные числа для денег (у `float` бывают ошибки вида `0.1 + 0.2 = 0.30000000000000004`).

## 1.3. Что такое Django

**Django** — веб-фреймворк на Python: набор готовых решений для типовых задач сайта. «Из коробки»: маршрутизация URL, ORM, шаблонизатор, формы, админ-панель, аутентификация, сессии, защита от типовых атак.

**Архитектура MVT (Model — View — Template):**

| Слой | Что делает | Где в проекте |
|---|---|---|
| **Model** | описывает данные и работу с БД | `products/models.py` |
| **View** | логика: получить запрос, взять данные, вернуть ответ | `*/views.py` |
| **Template** | внешний вид: HTML с подстановкой данных | `templates/*.html` |

Отличие от классического **MVC**: то, что в MVC называется Controller, в Django делит между собой сам фреймворк (диспетчер URL) и View; а Django-Template соответствует View из MVC.

**ORM (Object-Relational Mapping)** — работа с таблицами БД через классы и объекты Python вместо SQL. Класс = таблица, атрибут класса = столбец, объект = строка. `Product.objects.all()` → `SELECT * FROM products_product`.

**Проект vs приложение.** Проект (`WebApp1`) — весь сайт с настройками. Приложение (`products`, `pages`, `cart`) — компонент проекта, решающий одну задачу; подключается в `INSTALLED_APPS`.

## 1.4. Путь запроса через Django (главная схема — выучить)

```
Браузер: GET http://127.0.0.1:8000/detail/
   │
   ▼
Сервер разработки (runserver) ── интерфейс WSGI ──► Django
   │
   ▼
MIDDLEWARE (по списку сверху вниз): безопасность, сессии, CSRF, аутентификация
   │        → появляются request.session и request.user
   ▼
URL-диспетчер: ROOT_URLCONF = WebApp1/urls.py, перебирает urlpatterns сверху вниз,
   │           берёт ПЕРВОЕ совпадение  → product_detail_view
   ▼
View (products/views.py): obj = Product.objects.all()   ──► ORM ──► SQL ──► db.sqlite3
   │                      context = {"my_obj": obj}
   ▼
render(request, "product/detail.html", context)
   │   шаблонизатор находит файл (TEMPLATES → DIRS), подставляет контекст
   ▼
HttpResponse (готовый HTML) ──► MIDDLEWARE (в обратном порядке) ──► браузер
```

Ответ одной фразой: *«Запрос приходит на сервер, проходит через middleware, по `urls.py` находится представление, оно через модели берёт данные из БД, передаёт их в шаблон как контекст, `render` собирает HTML и возвращает его браузеру»*.

Все связи — **«один-ко-многим»** (`ForeignKey`): одна компания — много продуктов; один продукт — много экземпляров; один статус — много экземпляров; один пользователь — много заказанных экземпляров; один прайс-лист — много позиций; один продукт — много позиций в разных прайсах. `Pozition_Price` по сути связывает `Price` и `Product` «многие-ко-многим» с дополнительным атрибутом — ценой.

# Часть 3. Лабораторные 1–17

## ЛР 1. Установка ПО и создание проекта Django

**Что сделано:** проверил Python и pip → установил `virtualenv` → создал виртуальную среду `venv` → активировал → поставил `requests` (для демонстрации изоляции) и `django` → создал проект `django-admin startproject WebApp1` → запустил `python manage.py runserver` → открыл `http://127.0.0.1:8000/` → остановил Ctrl+C → поставил расширение Python в VS Code.

**Вопросы:**

**В: Что такое виртуальная среда и зачем она?**
О: Изолированная папка со своей копией интерпретатора Python, своим pip и своим набором пакетов. Нужна, чтобы у разных проектов были разные версии библиотек и они не конфликтовали; чтобы не засорять глобальный Python; чтобы легко передать проект другому: список пакетов выгружается `pip freeze > requirements.txt`, а у другого человека ставится `pip install -r requirements.txt`.

**В: Как доказать, что среда изолирована?**
О: `pip list` в активированной среде показывает `requests` и `Django`, а в другом окне консоли без активации — другой список, без них (кадры 09 и 10 в отчёте).

**В: Что делает активация?**
О: `venv\Scripts\activate` ставит папку `venv\Scripts` в начало переменной `PATH`, поэтому команды `python` и `pip` начинают означать интерпретатор из среды. Признак — префикс `(venv)` в приглашении. `deactivate` возвращает как было.

**В: Что такое pip? PATH?**
О: pip — система управления пакетами Python. PATH — системная переменная со списком папок, где ОС ищет исполняемые файлы по имени команды.

**В: Чем `virtualenv` отличается от `venv`?**
О: `venv` — встроенный в Python модуль, `virtualenv` — сторонний пакет с тем же назначением (появился раньше, умеет больше). По методичке ставим `virtualenv` и проверяем `python -m virtualenv -h`, а саму среду создаём `python -m venv venv`. Флаг `-m` — «запустить модуль как программу».

**В: Что делает `django-admin startproject WebApp1`?**
О: Создаёт каркас проекта: `manage.py` и пакет `WebApp1` с `settings.py`, `urls.py`, `wsgi.py`, `asgi.py`, `__init__.py`.

**В: Чем `django-admin` отличается от `manage.py`?**
О: `django-admin` — общая утилита Django, доступна везде. `manage.py` — то же самое, но привязано к конкретному проекту: выставляет переменную `DJANGO_SETTINGS_MODULE=WebApp1.settings`. Поэтому после создания проекта пользуемся `python manage.py ...`.

**В: Что делает `runserver`?**
О: Запускает встроенный сервер разработки на `127.0.0.1:8000`. Он однопоточно-простой, автоматически перезапускается при изменении кода, годится только для разработки (Django сам пишет предупреждение). Порт можно сменить: `python manage.py runserver 8080`.

**В: Почему в консоли нельзя вводить команды, пока сервер работает?**
О: Процесс сервера занимает консоль и выводит в неё журнал запросов. Остановка — Ctrl+C (или Ctrl+Break).

**В: Что за ракета на стартовой странице?**
О: Стандартная заглушка Django; показывается, пока `DEBUG=True` и в `urls.py` нет своих маршрутов для `/`.

**В: Почему проект лежит внутри папки `venv`?**
О: Так требует методичка. В реальной практике проект держат рядом с `venv`, а не внутри — среду не кладут в git и пересоздают.

**Вопросы:**

**В: Зачем `BASE_DIR`?**
О: Чтобы задавать пути относительно проекта, а не абсолютные (`BASE_DIR / 'db.sqlite3'`). Проект работает на любом компьютере и ОС. `Path` из `pathlib` делает пути независимыми от платформы.

**В: Почему `SECRET_KEY` нельзя публиковать?**
О: Им подписываются сессии и токены. Зная ключ, можно подделать подпись — например, сессию другого пользователя. У нас ключ с префиксом `django-insecure-` — это учебный ключ, в бою его выносят в переменные окружения.

**В: Что меняет `DEBUG`?**
О: При `True` — подробная «жёлтая» страница ошибки с трассировкой и настройками, автоперезагрузка сервера. При `False` — пользователю показывается сухая 404/500, обязательно нужно заполнить `ALLOWED_HOSTS`, статику и медиа должен раздавать настоящий веб-сервер. В продакшене — всегда `False`: страница ошибки раскрывает внутренности проекта.

**В: `ALLOWED_HOSTS = []` — почему сайт работает?**
О: При `DEBUG=True` и пустом списке Django сам разрешает `localhost`, `127.0.0.1` и `[::1]`. Любой другой хост получит 400 Bad Request. Защищает от подделки заголовка Host.

**В: Что в `INSTALLED_APPS` по умолчанию?**
О: `admin` — админ-панель; `auth` — пользователи, группы, права; `contenttypes` — учёт всех моделей (нужен для прав); `sessions` — сессии; `messages` — одноразовые уведомления; `staticfiles` — раздача статики.

**В: Что такое middleware?**
О: Цепочка обработчиков, через которые проходит каждый запрос до представления и каждый ответ после. Наши: `SecurityMiddleware` (заголовки безопасности), `SessionMiddleware` (создаёт `request.session`), `CommonMiddleware` (в т.ч. дописывает слэш в конце URL), `CsrfViewMiddleware` (защита форм), `AuthenticationMiddleware` (создаёт `request.user`), `MessageMiddleware`, `XFrameOptionsMiddleware` (запрет встраивать сайт во фрейм — защита от кликджекинга). **Порядок важен:** `AuthenticationMiddleware` стоит после `SessionMiddleware`, потому что пользователь определяется по сессии.

**В: Как перейти на PostgreSQL/MySQL?**
О: Поменять в `DATABASES` `ENGINE` (`django.db.backends.postgresql`), указать `NAME`, `USER`, `PASSWORD`, `HOST`, `PORT`, поставить драйвер и выполнить `migrate`. Код моделей и представлений не меняется — в этом смысл ORM.

**В: Почему SQLite?**
О: БД в одном файле, не требует установки сервера — удобно для обучения и разработки. Минус — плохо переносит много одновременных записей.

**В: Что такое `DEFAULT_AUTO_FIELD`?**
О: Тип автоматически создаваемого первичного ключа `id`. `BigAutoField` — 64-битное целое с автоинкрементом. В методичке эта строка есть в `settings.py`; в Django 6.x её в шаблоне нет, потому что `BigAutoField` стал значением по умолчанию (видно в миграциях: `('id', models.BigAutoField(...))`).

**В: WSGI и ASGI?**
О: WSGI (Web Server Gateway Interface) — стандартный интерфейс между веб-сервером и Python-приложением, синхронный. ASGI — его асинхронный преемник (веб-сокеты, async). `runserver` работает через WSGI — в консоли видно `<WSGIRequest: GET '/'>`.

## ЛР 3. Встроенные приложения Django

**Что сделано:** запустил сервер, увидел предупреждение о непримененных миграциях → `python manage.py migrate` → открыл `/admin` → создал суперпользователя `python manage.py createsuperuser` → вошёл в админку.

**Вопросы:**

**В: Что значит «You have N unapplied migration(s)»?**
О: У встроенных приложений (`admin`, `auth`, `contenttypes`, `sessions`) есть готовые миграции, но таблицы в БД ещё не созданы. `migrate` их применяет — появляются таблицы пользователей, групп, прав, сессий.

**В: Что делает `migrate`?**
О: Синхронизирует БД с моделями: выполняет ещё не применённые миграции (SQL-команды `CREATE TABLE`, `ALTER TABLE`). Что уже применено, Django помнит в таблице `django_migrations`.

**В: Кто такой суперпользователь?**
О: Пользователь с флагами `is_superuser=True`, `is_staff=True`, `is_active=True`. `is_superuser` — имеет все права без явного назначения. `is_staff` — может входить в админку. Создаётся `createsuperuser`.

**В: Почему пароль при вводе не виден? Как он хранится?**
О: Консоль скрывает ввод. В БД хранится не пароль, а **хеш**: строка вида `pbkdf2_sha256$<итерации>$<соль>$<хеш>`. Хеш необратим; при входе введённый пароль хешируется так же и сравнивается. **Соль** — случайная добавка, чтобы одинаковые пароли давали разные хеши.

**В: Что такое админ-панель и откуда она?**
О: Встроенное приложение `django.contrib.admin`. Автоматически строит интерфейс для просмотра, добавления, изменения и удаления записей зарегистрированных моделей. Маршрут — `path('admin/', admin.site.urls)`.

**В: Почему админка на английском?**
О: `LANGUAGE_CODE = 'en-us'`. Если поставить `'ru'` — станет русской. В методичке русский интерфейс — это автоперевод страницы браузером.

## ЛР 4. Создание приложения. Модели

**Что сделано:** `python manage.py startapp products` (и `profiles`, `cart`) → класс `Product` в `products/models.py` → `'products'` в `INSTALLED_APPS` → `makemigrations` → `migrate` → регистрация в `products/admin.py` → запись через админку и через `python manage.py shell` → методы `__str__` и класс `Meta`.

```python
class Product(models.Model):                      # наследование → это модель
    title = models.CharField(max_length=120, verbose_name="Название")
    description = models.TextField(blank=True, null=True, verbose_name="Описание")
    ...
    def __str__(self):                            # как объект показывается текстом
        return self.title
    class Meta:                                   # метаданные модели
        verbose_name = "Продукт",
        verbose_name_plural = "Продукты"
```

**Вопросы:**

**В: Что такое модель?**
О: Класс Python, наследник `django.db.models.Model`, описывающий таблицу БД. Атрибуты-поля → столбцы. Экземпляр класса → строка таблицы.

**В: Зачем наследоваться от `models.Model`?**
О: Без этого это обычный класс. Наследование даёт: создание таблицы миграциями, менеджер `objects` для запросов, методы `save()`, `delete()`, автоматическое поле `id`.

**В: Откуда столбец `id`, если я его не писал?**
О: Django сам добавляет первичный ключ `id` (`BigAutoField`, автоинкремент), если ни одно поле не помечено `primary_key=True`.

**В: Чем `makemigrations` отличается от `migrate`?** *(спросят почти наверняка)*
О: `makemigrations` сравнивает `models.py` с последним состоянием миграций и **создаёт файл миграции** (Python-описание изменений) в папке `migrations/`. БД при этом не трогается. `migrate` **применяет** файлы миграций к БД — выполняет SQL. Порядок всегда: изменил модель → `makemigrations` → `migrate`.

**В: Зачем приложение добавлять в `INSTALLED_APPS`?**
О: Иначе Django его «не видит»: не найдёт модели для миграций (`makemigrations` скажет «No changes detected»), не зарегистрирует в админке, не найдёт шаблоны и статику приложения.

**В: Как зарегистрировать модель в админке?**
О: В `admin.py`: `from .models import Product` и `admin.site.register(Product)`.

**В: Зачем `__str__`?**
О: Задаёт текстовое представление объекта. Без него в админке и в выпадающих списках будет «Product object (1)», с ним — название товара.

**В: Что такое `class Meta`?**
О: Вложенный класс с настройками модели, не являющимися полями: `verbose_name` / `verbose_name_plural` — название модели в единственном и множественном числе; `ordering` — сортировка по умолчанию; `db_table` — имя таблицы; индексы и ограничения.

**В: Как добавить запись без админки?**
О: `python manage.py shell` — интерактивная консоль Python с загруженным проектом:
```python
from products.models import Product
Product.objects.create(title="Ручка", description="Синяя")
Product.objects.all()
```

**В: Что делает `startapp`?**
О: Создаёт папку приложения с файлами `models.py`, `views.py`, `admin.py`, `apps.py`, `tests.py`, `__init__.py` и папкой `migrations/`.

**В: Зачем три приложения?**
О: Логическое разделение интернет-магазина: продукты, профили, корзина. `profiles` в итоге осталось пустым и в `INSTALLED_APPS` не подключено — задел методички, который дальше не использовался.

## ЛР 5. Изменение моделей

**Что сделано:** поменял типы полей (`title` → `CharField(max_length=120)`, `description` → `TextField(blank=True, null=True)`) → миграция 0002; добавил поле `ves` → Django спросил значение по умолчанию → добавил `blank=True` → миграция 0003; добавил `verbose_name` → миграция 0004; открыл `db.sqlite3` в SQLiteStudio.

**История миграций `products`:**

| № | Что делает | ЛР |
|---|---|---|
| 0001 | `CreateModel` Product (id, title, description) | 4 |
| 0002 | `AlterModelOptions` (verbose_name), `AlterField` title → CharField, description → null/blank | 4–5 |
| 0003 | `AddField` ves | 5 |

**Вопросы:**

**В: Чем `null=True` отличается от `blank=True`?** *(любимый вопрос)*
О: `null` — про **базу данных**: разрешает хранить в столбце `NULL`. `blank` — про **валидацию форм**: разрешает оставить поле пустым в форме/админке. Часто ставят вместе. Для строковых полей обычно достаточно `blank=True` — пустое значение хранится как пустая строка `''`.

**В: Почему при добавлении поля `ves` Django задал вопрос?**
О: В таблице уже были записи, а новое поле обязательное (NOT NULL) и без значения по умолчанию — Django не знает, чем его заполнить в существующих строках. Варианты: 1) ввести разовое значение по умолчанию прямо в консоли; 2) выйти и исправить модель — задать `default=...`, либо `null=True`, либо (для текстового поля) `blank=True`. Я выбрал второй путь: с `blank=True` у `TextField` Django сам подставляет пустую строку и вопроса не задаёт.

**В: Что внутри файла миграции?**
О: Класс `Migration` с двумя атрибутами: `dependencies` — от каких миграций зависит (обычно от предыдущей — так выстраивается цепочка), и `operations` — список операций: `CreateModel`, `AddField`, `AlterField`, `AlterModelOptions`, `DeleteModel`. `initial = True` — у первой.

**В: Можно ли откатить миграцию?**
О: Да: `python manage.py migrate products 0003` — вернёт БД к состоянию после 0003. `migrate products zero` — откатит все. `showmigrations` — список со статусом; `sqlmigrate products 0003` — покажет SQL.

**В: `CharField` vs `TextField`?**
О: `CharField` — короткая строка, `max_length` обязателен (в БД `varchar(120)`), в форме — однострочный `<input>`. `TextField` — текст произвольной длины, в форме — `<textarea>`.

**В: Что такое `verbose_name` у поля?**
О: Человекочитаемое название поля — подпись в админке и в ModelForm. Без него берётся имя атрибута («Title»).

**В: Изменение `verbose_name` не меняет структуру таблицы — зачем миграция?**
О: Миграции фиксируют полное состояние модели, а не только SQL-структуру. Миграция 0004 создаётся, но в БД по факту ничего не меняет.

**В: Почему название поля в админке жирное?**
О: Жирным выделены обязательные поля (у которых нет `blank=True`).

**В: Как называется таблица модели `Product`?**
О: `products_product` — `<имя приложения>_<имя модели>` в нижнем регистре. Можно переопределить через `Meta.db_table`.

**В: Какие ещё типы полей знаешь?**
О: `IntegerField`, `DecimalField(max_digits, decimal_places)`, `FloatField`, `BooleanField`, `DateField`, `DateTimeField`, `EmailField`, `SlugField`, `ImageField`, `FileField`, `ForeignKey`, `ManyToManyField`, `OneToOneField`.

**В: Вес хранится как `TextField` — это нормально?**
О: Так задано методичкой. Правильнее `DecimalField` или `IntegerField` — тогда можно сортировать и считать, и нельзя ввести «abc».

## ЛР 6. Связи между таблицами

**Что сделано:** модель `Company`; в `Product` — поле `company = ForeignKey(Company, ...)`; модели `Status` и `ProductInstance` с двумя внешними ключами; миграции 0005, 0006; регистрация в админке; заполнение данными.

```python
company = models.ForeignKey(Company, on_delete=models.CASCADE, blank=True, null=True, ...)
```

**Вопросы:**

**В: Что такое `ForeignKey`?**
О: Внешний ключ — связь «многие-к-одному» («один-ко-многим»): много продуктов ссылаются на одну компанию. Ставится на стороне «многих».

**В: В модели поле `company`, а в БД столбец `company_id` — почему?**
О: Django к имени поля-связи добавляет `_id` — в столбце хранится число, id связанной записи. В коде `product.company` — это уже **объект** `Company` (Django сам делает запрос), а `product.company_id` — просто число.

**В: Что такое `on_delete`?** *(спросят)*
О: Что делать с записью, когда удаляют ту, на которую она ссылается. Обязательный параметр.

| Значение | Поведение |
|---|---|
| `CASCADE` | удалить и зависимые записи (удалили компанию — удалились её продукты) |
| `SET_NULL` | записать NULL (нужен `null=True`) — у нас для `customer` |
| `PROTECT` | запретить удаление, пока есть ссылки |
| `SET_DEFAULT` | подставить значение по умолчанию |
| `DO_NOTHING` | ничего не делать (риск нарушить целостность) |

**В: Почему у `customer` `SET_NULL`, а у остальных `CASCADE`?**
О: При удалении пользователя экземпляр товара должен остаться — просто без заказчика. А экземпляр без продукта не имеет смысла, поэтому каскад.

**В: Что будет, если удалить компанию?**
О: Каскадно удалятся её продукты, а за ними — их экземпляры (`ProductInstance`) и позиции прайса (`Pozition_Price`). Админка перед удалением покажет список всего, что будет удалено.

**В: Какие типы связей есть в Django?**
О: `ForeignKey` — один-ко-многим; `ManyToManyField` — многие-ко-многим (Django создаёт промежуточную таблицу); `OneToOneField` — один-к-одному (например, профиль пользователя).

**В: Как получить название компании продукта? А все продукты компании?**
О: Прямая связь: `Product.objects.get(id=1).company.name`. Обратная: `company.product_set.all()` — Django автоматически создаёт менеджер `<модель>_set`.

**В: Почему в `ProductInstance` связь записана строкой `'Product'`, а в `Product` — классом `Company`?**
О: Оба варианта допустимы. Строка нужна, когда класс объявлен ниже по файлу или в другом приложении (`'app.Model'`). `Company` объявлен выше `Product`, поэтому можно классом.

**В: Зачем отдельная модель `ProductInstance`?**
О: `Product` — это вид товара. У одного вида много экземпляров, и у каждого своё состояние: один на складе, другой в заказе. Это нормализация: общие сведения хранятся один раз в `Product`, а не дублируются.

**В: Зачем `Status` отдельной таблицей?**
О: Справочник: статус хранится один раз, экземпляры ссылаются по id. Можно переименовать статус в одном месте, нельзя ввести опечатку. Альтернатива — поле с `choices`.

**В: Что такое первичный и внешний ключ?**
О: Первичный (PK) — уникальный идентификатор строки (`id`). Внешний (FK) — столбец, хранящий PK строки другой таблицы; БД гарантирует, что такая строка существует (ссылочная целостность).

## ЛР 7. Создание страниц сайта

**Что сделано:** приложение `pages` → функции-представления в `pages/views.py` → маршруты в `WebApp1/urls.py` → вывод `args`, `kwargs`, `request`, `request.user` в консоль.

```python
def home_view(request, *args, **kwargs):
    print(args, kwargs)      # () {}
    print(request)           # <WSGIRequest: GET '/'>
    print(request.user)      # admin  или  AnonymousUser
    return render(request, "home.html", {})
```

```python
path('contact/', views.contact_view),
```

**Вопросы:**

**В: Что такое представление (view)?**
О: Функция или класс Python, которая принимает объект запроса `request` и возвращает объект ответа `HttpResponse`. Здесь пишется логика страницы.

**В: Что такое `HttpResponse`?**
О: Класс ответа из `django.http`. В него можно передать строку с HTML: `HttpResponse("<h1>Hello</h1>")`. Самый простой, но непрактичный способ — вся разметка внутри Python-кода.

**В: Что такое маршрутизация?**
О: Сопоставление URL-адреса и представления. `ROOT_URLCONF` указывает на `WebApp1/urls.py`, в нём список `urlpatterns`. Django отрезает домен, берёт путь и идёт по списку **сверху вниз до первого совпадения**. Не нашёл — 404.

**В: Разбери `path('contact/', views.contact_view, name='...')`.**
О: 1-й аргумент — шаблон пути (без ведущего слэша); 2-й — функция-представление, передаётся **без скобок** (мы отдаём саму функцию, Django вызовет её сам); 3-й, необязательный — имя маршрута для `{% url %}` и `reverse()`.

**В: Почему была ошибка 404 на `/home_view/`?**
О: Функция существовала, но не была привязана ни к какому адресу в `urls.py`. Django не вызывает представления по имени функции.

**В: Что в `request`?**
О: Объект `WSGIRequest` со всеми данными запроса: `request.method` (`'GET'`/`'POST'`), `request.GET`, `request.POST` (данные формы), `request.user` (кто отправил), `request.session` (сессия), `request.path` (путь), `request.FILES`, `request.COOKIES`.

**В: Зачем `*args, **kwargs`? Почему они пустые?**
О: Чтобы функция приняла любые дополнительные аргументы. В `kwargs` попадают параметры из URL: для `path('x/<int:id>', ...)` было бы `{'id': 5}`. У главной страницы параметров в адресе нет — оба пусты.

**В: Почему в одном браузере `admin`, а в другом `AnonymousUser`?**
О: Вход запоминается через cookie `sessionid`, а cookie у каждого браузера свои. В первом я вошёл в админку — запрос идёт с cookie, и `AuthenticationMiddleware` определяет пользователя. Во втором cookie нет — Django подставляет специальный объект `AnonymousUser`.

**Вопросы:**

**В: Что такое шаблон?**
О: HTML-файл со специальной разметкой шаблонизатора Django: `{{ переменная }}` — вывод значения, `{% тег %}` — логика (циклы, условия, наследование), `{{ x|фильтр }}` — преобразование, `{# ... #}` — комментарий.

**В: Что делает `render(request, "home.html", context)`?**
О: Находит шаблон, подставляет в него данные из словаря `context` и возвращает `HttpResponse` с готовым HTML. Три аргумента: запрос, имя шаблона, контекст.

**В: Что такое контекст?**
О: Словарь Python, передаваемый из представления в шаблон. Ключи становятся именами переменных в шаблоне. Значения — любые: строки, числа, списки, объекты и наборы объектов из БД.

**В: Почему была ошибка `TemplateDoesNotExist` и как исправлена?**
О: Сначала файла не было вообще. Потом файл был, но Django не знал, где искать: `DIRS` был пуст. Прописал `BASE_DIR/templates` — заработало.

**В: Где Django ищет шаблоны?**
О: Сначала в папках из `DIRS`, затем (при `APP_DIRS: True`) в папке `templates` каждого подключённого приложения. Берёт первый найденный.

**В: `{% extends %}` vs `{% include %}`?** *(спросят)*
О: `extends` — **наследование**: дочерний шаблон берёт весь каркас родителя и заменяет только блоки `{% block %}`. `include` — **вставка**: содержимое другого файла подставляется в это место. У нас `home.html` наследует `base.html`, а `base.html` включает `navbar.html`.

**В: Зачем базовый шаблон?**
О: Чтобы не дублировать общие части (head, подключение Bootstrap, меню) на каждой странице. Правка в одном месте применяется ко всему сайту. Принцип DRY — Don't Repeat Yourself.

**В: Что будет, если дочерний шаблон не переопределит блок?**
О: Выведется содержимое блока из родителя — у нас текст «эта часть будет заменена».

**В: Что такое `forloop.counter`?**
О: Служебная переменная внутри `{% for %}` — номер итерации с 1. Есть ещё `forloop.counter0` (с нуля), `forloop.first`, `forloop.last`.

**В: Откуда в шаблоне `user` и `request`, если я их не передавал в контекст?**
О: Из **контекстных процессоров** (`TEMPLATES → OPTIONS → context_processors`). `auth` добавляет `user` в каждый шаблон, `request` — объект запроса. Работают автоматически при использовании `render`.

**В: Можно ли в шаблоне писать Python-код?**
О: Нет. Язык шаблонов намеренно ограничен: вывод, условия, циклы, фильтры. Логика должна быть в представлении. Методы без аргументов вызываются без скобок: `{{ user.get_full_name }}`.

**Вопросы:**

**В: Что такое `Product.objects`?**
О: **Менеджер** модели — через него выполняются запросы к таблице. `all()`, `get()`, `filter()`, `create()` — его методы.

**В: `all()` vs `get()` vs `filter()`?** *(спросят)*
О: `all()` — все записи, возвращает QuerySet. `filter(условие)` — подходящие записи, QuerySet (возможно пустой). `get(условие)` — **ровно один объект**; если не найдено — исключение `DoesNotExist`, если найдено несколько — `MultipleObjectsReturned`.

**В: Что такое QuerySet?**
О: Набор объектов модели — результат запроса. Он **ленивый**: SQL выполняется не при создании, а когда данные реально понадобились (перебор в цикле, `len()`, срез). QuerySet'ы можно цеплять: `.filter(...).filter(...).order_by(...)` — получится один SQL-запрос.

**В: Как `id` попадает в функцию?**
О: `<int:id>` в маршруте — **конвертер пути**: вырезает из URL кусок, проверяет что это целое число, превращает в `int` и передаёт в представление именованным аргументом `id`. Другие конвертеры: `str`, `slug`, `uuid`, `path`.

**В: Что будет при `/detail_product/abc`? При `/detail_product/9999`?**
О: `abc` — не число, маршрут не совпадёт → 404. `9999` — маршрут совпадёт, но `get()` выбросит `Product.DoesNotExist` → ошибка 500 (в режиме отладки — жёлтая страница). Правильнее — `get_object_or_404(Product, id=id)`, который вернёт 404.

**В: Что такое фильтр шаблона?**
О: Преобразование значения при выводе: `{{ значение|фильтр:аргумент }}`. `truncatechars:9` обрезает строку до 9 символов (включая многоточие). Другие: `upper`, `lower`, `length`, `date:"d.m.Y"`, `default:"нет"`, `safe`.

**В: Почему шаблон указан как `"product/detail.html"`?**
О: Это путь относительно папки `templates`: файл лежит в `templates/product/detail.html`. Подпапки — для порядка.

**В: Сколько SQL-запросов на странице списка?**
О: Один — `SELECT` всех продуктов, выполняется в момент начала цикла `{% for %}`.

## ЛР 10. Форма создания записи

**Что сделано:** `products/forms.py` с классом `ProductForm` → представление `product_create_view` → шаблон `product/product_create.html` → параметры `required`, `label`, `widget`.

```python
class ProductForm(forms.Form):
    title = forms.CharField(required=True, label="Название *",
                            widget=forms.TextInput(attrs={"placeholder": "Название продукта"}))
    description = forms.CharField(required=True, label="Описание *",
                            widget=forms.Textarea(attrs={"placeholder": "...", "rows": 5, "cols": 25}))

```
```python
def product_create_view(request):
    form = ProductForm()                               # пустая форма
    if request.method == "POST":
        form = ProductForm(request.POST)               # форма с присланными данными
        if form.is_valid():                            # проверка
            Product.objects.create(**form.cleaned_data)   # запись в БД
    form = ProductForm()                               # очистка формы
    return render(request, "product/product_create.html", {"form": form})
```
```django
<form action="." method="POST"> {% csrf_token %}
    {{ form.as_p }}
    <input type='submit' value='Сохранить'/>
</form>
```

**Вопросы:**

**В: Что такое форма Django и зачем она, если есть HTML `<form>`?**
О: Класс Python, описывающий поля формы. Даёт три вещи: 1) **генерацию HTML** полей; 2) **валидацию** данных на сервере; 3) **очистку** — преобразование строк из запроса в типы Python (`cleaned_data`).

**В: Разбери работу представления по шагам.**
О: Первый заход — GET: создаётся пустая форма, отрисовывается. Пользователь заполняет и жмёт «Сохранить» — браузер шлёт POST на тот же адрес. `ProductForm(request.POST)` — форма «привязывается» к данным. `is_valid()` запускает проверку. Если всё хорошо — данные лежат в `form.cleaned_data`, из них создаётся запись. Потом форма создаётся заново пустой и страница отрисовывается снова.

**В: Что делает `**form.cleaned_data`?**
О: `cleaned_data` — словарь `{'title': ..., 'description': ..., 'ves': ...}`. `**` распаковывает его в именованные аргументы: `Product.objects.create(title=..., description=..., ves=...)`. Работает, потому что имена полей формы совпадают с именами полей модели.

**В: Что делает `is_valid()`?**
О: Проверяет каждое поле: обязательность, тип, длину. Возвращает `True`/`False`. Заполняет `form.cleaned_data` (чистые данные) и `form.errors` (ошибки).

**В: Что такое `{% csrf_token %}`?** *(спросят обязательно)*
О: Защита от **CSRF** (Cross-Site Request Forgery — межсайтовая подделка запроса). Атака: пользователь залогинен на нашем сайте, заходит на вредоносный сайт, и тот от его имени отправляет форму на наш — браузер сам приложит cookie сессии. Защита: Django вставляет в форму скрытое поле `csrfmiddlewaretoken` со случайным токеном и кладёт парный в cookie; `CsrfViewMiddleware` при POST сверяет их. Чужой сайт токен узнать не может. Без тега — ошибка **403 Forbidden**.

**В: Почему POST, а не GET?**
О: Форма изменяет БД. По стандарту HTTP GET не должен ничего менять; данные GET видны в URL, попадают в историю и логи; CSRF-защита работает только для POST.

**В: Что такое `action="."`?**
О: Адрес, куда отправить форму. `.` — текущий адрес, то есть то же представление, что отрисовало страницу. Пустой `action` даёт тот же эффект.

**В: Что такое `form.as_p`?**
О: Вывести все поля формы, обернув каждое в `<p>`. Есть `as_table`, `as_ul`, `as_div`; можно выводить поля по одному — `{{ form.title }}`, `{{ form.title.label_tag }}`, `{{ form.title.errors }}`.

**В: Что такое widget?**
О: Определяет, каким HTML-элементом рисуется поле. У каждого типа поля есть виджет по умолчанию: у `CharField` — `TextInput` (`<input type="text">`). Заменил на `Textarea` для описания. `attrs` — HTML-атрибуты элемента: `placeholder`, `rows`, `cols`, `class`.

**В: Что делает `required`? `label`?**
О: `required=True` (по умолчанию) — поле обязательно: Django добавит HTML-атрибут `required` (браузер не даст отправить пустую форму) и проверит на сервере. `label` — подпись поля.

**В: `forms.Form` vs `forms.ModelForm`?**
О: `Form` — поля описываются вручную, сохранение пишем сами. `ModelForm` — поля генерируются из модели (`class Meta: model = ...; fields = ...`), есть метод `save()`. У нас `ProductForm` — обычная `Form`, а `RegistrForm` (ЛР 15) — `ModelForm`.

**В: Нужна ли серверная валидация, если браузер уже проверяет `required`?**
О: Обязательно. Проверку в браузере легко обойти — отправить запрос напрямую или убрать атрибут через инструменты разработчика. Доверять можно только серверной проверке.

**В: Что считает `count()`?**

**В: Что значит `filter(status_id__exact=2)`?**

**В: Что такое класс-представление (CBV) и `ListView`?**
О: Представление в виде класса, а не функции. Django даёт готовые **обобщённые** классы для типовых задач: `ListView` — список объектов, `DetailView` — один объект, `CreateView`/`UpdateView`/`DeleteView` — формы. Достаточно указать `model = Company`, остальное `ListView` делает сам: запрашивает все записи, ищет шаблон, передаёт данные.

**В: Откуда `ListView` знает шаблон и имя переменной?**
О: По соглашению. Шаблон: `<приложение>/<модель>_list.html` → `products/company_list.html`. Переменные контекста: `object_list` и `<модель>_list` → `company_list`. Переопределяются атрибутами `template_name` и `context_object_name`.

**В: Зачем `.as_view()` в `urls.py`?**
О: `path()` ждёт функцию, а `CompanyView` — класс. Метод `as_view()` возвращает функцию-обёртку, которая на каждый запрос создаёт экземпляр класса и вызывает нужный метод (`get` или `post`).

**В: Функции или классы — что лучше?**
О: Функции проще и нагляднее, вся логика на виду. Классы дают меньше кода на типовых задачах и переиспользование через наследование и миксины, но логика скрыта в родителях.

**В: `path` vs `re_path`?**
О: `path` — простой синтаксис с конвертерами `<int:id>`, совпадение по **всей строке**. `re_path` — регулярное выражение, совпадение по **поиску подстроки** (нужны `^` и `$`, чтобы ограничить). См. часть 5, п. 4.

**В: Как работает удаление?**
О: Ссылка «Удалить» ведёт на `/product_delete/<id>`. Представление находит объект, вызывает `delete()` (SQL `DELETE`, плюс каскад по связям) и перенаправляет на список.

**В: `redirect`, `reverse`, `HttpResponseRedirect` — в чём разница?**
О: `reverse('имя')` — **строит URL по имени маршрута** (`'product_detail'` → `/detail/`). `HttpResponseRedirect(url)` — ответ с кодом 302 и заголовком `Location`. `redirect(...)` — удобная обёртка: принимает URL, имя маршрута или объект. Использовать имена лучше, чем жёсткие адреса: при смене адреса в `urls.py` ничего не сломается.

**В: Как работает редактирование?**
О: GET — объект достаётся из БД, его поля подставляются в `value` полей формы. POST — значения берутся из `request.POST.get('title')`, присваиваются атрибутам объекта, `save()` выполняет SQL `UPDATE`, затем редирект на список.

**В: `create()` vs `save()`?**
О: `Model.objects.create(...)` — создать объект и сразу сохранить (INSERT). `obj.save()` — сохранить существующий объект: если у него есть `id` — UPDATE, если нет — INSERT.

**В: Зачем редирект после POST?**
О: Шаблон **Post/Redirect/Get**: если после POST сразу отдать страницу, обновление (F5) отправит форму повторно. После редиректа F5 повторит безопасный GET.

**Вопросы:**

**В: Аутентификация vs авторизация?** *(спросят обязательно)*
О: **Аутентификация** — проверка, *кто ты* (логин и пароль). **Авторизация** — проверка, *что тебе разрешено* (права, флаги, группы). Сначала первое, потом второе.

**В: Что даёт `django.contrib.auth` из коробки?**
О: Модели `User`, `Group`, `Permission`; хеширование паролей; готовые представления и формы входа, выхода, смены и сброса пароля; готовые URL-адреса. **Не даёт шаблонов** — их пишем сами в папке `templates/registration/`.

**В: Что делает `include('django.contrib.auth.urls')`?**
О: Подключает набор готовых маршрутов с префиксом `accounts/`: `login/`, `logout/`, `password_change/`, `password_reset/` и др. `include` — способ вынести маршруты в отдельный файл и подключить группой.

**В: Почему шаблон должен лежать именно в `registration/login.html`?**
О: Встроенный `LoginView` по умолчанию ищет шаблон с именем `registration/login.html`. В шаблон он передаёт `form` (`AuthenticationForm` с полями `username`, `password`) и `next`.

**В: Что происходит при входе?**
О: `LoginView` получает POST → форма проверяет логин и пароль (хеширует введённый пароль и сравнивает с хешем в `auth_user`) → вызывается `login()`: в сессию записывается id пользователя, браузер получает cookie `sessionid` → редирект. При следующих запросах `AuthenticationMiddleware` по сессии находит пользователя и кладёт в `request.user`.

**В: Зачем `LOGIN_REDIRECT_URL`?**
О: Куда направить после успешного входа. По умолчанию — `/accounts/profile/`, такой страницы нет → была ошибка 404. Поставил `'/'` — на главную.

**В: Что такое параметр `next`?**
О: Адрес, с которого пользователя отправили на вход. После входа Django возвращает туда. Пример: гость открыл `/borrowed/` → редирект на `/accounts/login/?next=/borrowed/` → после входа попадёт на `/borrowed/`.

**В: Что делают `is_authenticated`, `is_staff`, `is_superuser`, `is_active`?**
О: `is_authenticated` — `True` у вошедшего, `False` у `AnonymousUser`. `is_staff` — доступ в админку. `is_superuser` — все права. `is_active` — учётная запись не отключена (неактивный не может войти).

**В: Зачем группы?**
О: Чтобы выдавать права не каждому пользователю отдельно, а группе — все участники их наследуют. У нас группа без прав, создана по методичке.

**В: Что такое права (permissions)?**
О: Для каждой модели Django автоматически создаёт 4 права: `add`, `change`, `delete`, `view`. Назначаются пользователю или группе, проверяются `user.has_perm('products.add_product')`, в шаблоне — `perms.products.add_product`.

**В: Почему «Выход» сделан формой с кнопкой, а не ссылкой?**
О: Начиная с Django 5.0 `LogoutView` принимает только POST — выход меняет состояние и должен быть защищён от CSRF (иначе любой сайт мог бы разлогинить пользователя картинкой со ссылкой). GET на `/accounts/logout/` возвращает 405. В методичке (Django 4.0) была ссылка — это адаптация под новую версию.

**В: Почему `login.html` выглядит без оформления?**
О: Он не наследует `base.html` — так в методичке.

## ЛР 13. Заказы пользователя

**Что сделано:** в `ProductInstance` добавил `customer = ForeignKey(User, on_delete=SET_NULL, ...)` → миграция 0007 → назначил заказчиков в админке → `LoanedProductByUserListView` («Мои заказы») → «Работа со справочниками» только для суперпользователя → `LoanedProductAllListView` («Все заказы») для персонала.

```python
class LoanedProductByUserListView(LoginRequiredMixin, generic.ListView):
    model = ProductInstance
    template_name = 'product/productinstance_list_customer_user.html'
    paginate_by = 10

    def get_queryset(self):
        return ProductInstance.objects.filter(customer=self.request.user) \
                                      .filter(status_id__exact=2).order_by('due_back')
```

**Вопросы:**

**В: Как связать заказ с пользователем?**
О: Внешний ключ на встроенную модель `User` из `django.contrib.auth.models`. В БД появился столбец `customer_id`.

**В: Что такое `LoginRequiredMixin`?**
О: Класс-примесь: добавляет проверку «пользователь вошёл?» до выполнения представления. Гостя перенаправляет на `LOGIN_URL` (`/accounts/login/`) с параметром `?next=`. Должен стоять **первым** в списке родителей. Для функций аналог — декоратор `@login_required`.

**В: Что такое миксин?**
О: Небольшой класс, добавляющий одну возможность через множественное наследование. Сам по себе не используется.

**В: Зачем переопределён `get_queryset`?**
О: По умолчанию `ListView` вернул бы **все** записи модели. Переопределяю, чтобы показать только экземпляры текущего пользователя (`customer=self.request.user`) со статусом 2, отсортированные по дате.

**В: Чем `self.request.user` отличается от `request.user`?**
О: Это тот же объект. В классе-представлении запрос хранится в атрибуте `self.request`.

**В: `order_by('due_back')` и `order_by('-due_back')`?**
О: Без минуса — по возрастанию, с минусом — по убыванию.

**В: Что такое `paginate_by = 10`?**
О: Разбивка на страницы по 10 записей; номер страницы — параметр `?page=2`. В шаблон передаётся `page_obj`. Ссылок переключения страниц в шаблоне нет — записей мало.

**В: Что такое `context_object_name`?**
О: Имя переменной со списком в шаблоне. У `LoanedProductAllListView` задано явно `'productinstance_list'` — оно совпадает с именем по умолчанию.

**В: Как пользователь с одним логином не видит чужие заказы?**
О: Фильтрация на сервере по `request.user`. Пользователь не может подменить id в запросе — он берётся из сессии.

## ЛР 14. Настройка админ-панели

**Что сделано:** вместо `admin.site.register(Product)` — класс `ProductAdmin`; `ProductInstanceAdmin` с секциями; встроенное редактирование экземпляров; вычисляемый столбец; поиск. Файл `products/admin.py`.

```python
class ProductInstanceInline(admin.TabularInline):
    model = ProductInstance

class ProductAdmin(admin.ModelAdmin):
    list_display = ('title', 'description', 'ves', 'company', 'show_count')
    list_filter = ('company',)
    prepopulated_fields = {'slug': ('title',)}
    inlines = [ProductInstanceInline]
    search_fields = ("title__startswith",)

    def show_count(self, obj):
        from django.db.models import Count
        result = ProductInstance.objects.filter(product=obj).aggregate(Count('product'))
        return result["product__count"]
    show_count.short_description = "Количество,шт"

admin.site.register(Product, ProductAdmin)
```

| Атрибут `ModelAdmin` | Что делает |
|---|---|
| `list_display` | столбцы в списке записей (поля модели или методы) |
| `list_filter` | панель фильтров справа |
| `search_fields` | строка поиска и по каким полям искать |
| `fields` | какие поля и в каком порядке на форме |
| `fieldsets` | разбивка формы на секции с заголовками |
| `inlines` | редактирование связанных записей на этой же странице |
| `prepopulated_fields` | автозаполнение поля из других (slug из title) |
| `ordering`, `list_per_page`, `readonly_fields`, `list_editable` | сортировка, размер страницы, только чтение, правка прямо в списке |

**Вопросы:**

**В: Что такое `ModelAdmin`?**
О: Класс, описывающий, как модель отображается в админке. Регистрируется вторым аргументом: `admin.site.register(Product, ProductAdmin)`. Альтернатива — декоратор `@admin.register(Product)`.

**В: Зачем запятая в `list_filter = ('company',)`?**
О: Это кортеж из одного элемента. Без запятой `('company')` — просто строка в скобках.

**В: Что такое inline? `TabularInline` vs `StackedInline`?**
О: Возможность редактировать связанные (дочерние) записи прямо на странице родителя: на странице продукта — его экземпляры. `TabularInline` — таблицей (каждая запись — строка), `StackedInline` — блоками друг под другом.

**В: Как работает `show_count`?**
О: Метод `ModelAdmin`, вызывается для каждой строки списка; `obj` — продукт этой строки. `filter(product=obj)` отбирает экземпляры продукта, `aggregate(Count('product'))` считает их на стороне БД и возвращает **словарь** `{'product__count': 2}`. `short_description` — заголовок столбца.

**В: `aggregate` vs `annotate`?**
О: `aggregate` — одно итоговое значение по всему набору, возвращает словарь. `annotate` — добавляет вычисленное значение **каждому объекту** набора. Агрегатные функции: `Count`, `Sum`, `Avg`, `Min`, `Max`.

**В: Можно ли посчитать проще?**
О: Да: `obj.productinstance_set.count()`.

**В: Что значит `title__startswith` в `search_fields`?**
О: Искать записи, у которых название **начинается** с введённого текста (SQL `LIKE 'текст%'`). Без модификатора поиск был бы по вхождению (`icontains`).

**В: Что такое `fieldsets`?**
О: Кортеж пар «заголовок секции — словарь с `fields`». Делит форму на секции: «Экземпляр продукта» (инв. номер, продукт) и «Статус и окончание его действия» (заказчик, статус, дата).

**В: Что такое `prepopulated_fields`?**
О: Поле `slug` заполняется автоматически по мере ввода `title` — скриптом JavaScript в админке. Работает только при создании записи в админке.

## ЛР 15. Регистрация пользователя

**Что сделано:** шаблоны `registration/registration.html` и `registration_out.html` → форма `RegistrForm` (наследник `UserCreationForm`) → представление `registrat` → маршрут `registr/`.

```python
class RegistrForm(UserCreationForm):
    email = forms.EmailField(max_length=254, help_text='Поле обязательное для заполнения')
    first_name = forms.CharField(required=True, label="Ваше имя", max_length=254)
    last_name = forms.CharField(required=True, label="Ваша фамилия", max_length=254)

    class Meta:
        model = User
        fields = ('first_name', 'last_name', 'email', 'username', 'password1', 'password2',)
```
```python
def registrat(request):
    data = {}
    if request.method == 'POST':
        form = RegistrForm(request.POST)
        if form.is_valid():
            new_user = form.save(commit=False)
            new_user.save()
            data['form'] = form
            return render(request, 'registration/registration_out.html', data)
    else:
        form = RegistrForm()
        data['form'] = form
    return render(request, 'registration/registration.html', data)
```

**Вопросы:**

**В: Что такое `UserCreationForm`?**
О: Встроенная `ModelForm` для модели `User` с полями `username`, `password1`, `password2`. Проверяет: логин не занят, пароли совпадают, пароль проходит `AUTH_PASSWORD_VALIDATORS`. Её метод `save()` **хеширует пароль** (`set_password`) и сохраняет пользователя.

**В: Как добавлены email, имя и фамилия?**
О: Наследованием: `RegistrForm(UserCreationForm)` — объявил три новых поля и перечислил их в `Meta.fields`. Имена совпадают с полями модели `User`, поэтому `ModelForm` сама записывает их в объект. Порядок в `fields` задаёт порядок на странице.

**В: Зачем два поля пароля?**
О: Защита от опечатки: пароль вводится вслепую, форма проверяет совпадение. В БД сохраняется один хеш.

**В: Какие проверки пароля?**
О: Четыре валидатора из `settings.py`: не похож на логин/имя/email; не короче 8 символов; не из списка распространённых; не состоит только из цифр.

**В: Что значит `save(commit=False)`?**
О: Создать объект `User` из данных формы (пароль уже захеширован), но **не записывать в БД**. Нужен, чтобы что-то дописать в объект перед сохранением. Затем `new_user.save()`. В нашем коде между ними ничего нет, так что это равносильно `form.save()`.

**В: Почему закомментирована строка `set_password`?**
О: Она не нужна и ошибочна: `UserCreationForm.save()` уже хеширует пароль, а поля `password` в `cleaned_data` нет — есть `password1` и `password2`.

**В: Почему нельзя просто написать `user.password = '123'`?**
О: Так пароль запишется открытым текстом, и вход работать не будет — Django сравнивает хеши. Нужно `user.set_password('123')`.

**В: Какие права у зарегистрированного?**
О: Обычный активный пользователь: `is_staff=False`, `is_superuser=False`. В админку войти не может, меню «Работа со справочниками» и «Все заказы» не видит.

**В: Пользователь после регистрации сразу вошёл?**
О: Нет — показывается страница «Регистрация прошла успешно» со ссылкой на вход. Для автоматического входа надо было бы вызвать `login(request, new_user)`.

**В: Что такое `help_text`?**
О: Подсказка, выводимая рядом с полем формы.

## ЛР 16. Интернет-магазин: изображения, цены, сессии

**Что сделано:** `pip install pillow` → модели `Price`, `Pozition_Price` → в `Product` поля `slug` и `image` → миграции 0008, 0009 → `MEDIA_URL`/`MEDIA_ROOT` и раздача медиа в `urls.py` → `product_list` и `product_detail` → `products/urls.py` и `include` → `get_absolute_url` → `CART_SESSION_ID` → начало класса `Cart`.

```python
slug = models.SlugField(max_length=200, db_index=True, allow_unicode=True, ...)
image = models.ImageField(upload_to='images/', blank=True, ...)

def get_absolute_url(self):
    return reverse('detail_product', args=[self.id])
```
```python
# settings.py
MEDIA_URL = '/media/'
MEDIA_ROOT = Path.joinpath(BASE_DIR, "media")
CART_SESSION_ID = 'cart'
```
```python
# urls.py
if settings.DEBUG:
    urlpatterns += static(settings.MEDIA_URL, document_root=settings.MEDIA_ROOT)
```

**Вопросы:**

**В: Зачем Pillow?**
О: Библиотека обработки изображений. `ImageField` требует её: проверяет, что загруженный файл — действительно изображение, определяет размеры. Без Pillow Django не даст создать миграцию с `ImageField`.

**В: Где хранится картинка?** *(спросят)*
О: **Файл** — на диске в `MEDIA_ROOT/images/` (`upload_to='images/'`). **В БД** — только относительный путь строкой: `images/karandash.png`. В шаблоне `{{ product.image.url }}` даёт `MEDIA_URL` + путь = `/media/images/karandash.png`.

**В: Static vs media?** *(спросят)*
О: **Static** — файлы самого сайта, часть кода: CSS, JS, картинки оформления; лежат в `static/`, подключаются `{% load static %}` и `{% static 'путь' %}`. **Media** — файлы, загруженные пользователями/администратором в процессе работы; лежат в `media/`, адрес берётся из `.url`.

**В: Зачем `if settings.DEBUG: urlpatterns += static(...)`?**
О: Сервер разработки сам не раздаёт медиа. Функция `static()` добавляет маршрут `/media/...`, отдающий файлы из `MEDIA_ROOT`. Только в режиме отладки: в продакшене файлы должен отдавать веб-сервер (nginx) — это быстрее и безопаснее.

**В: Что такое slug?**
О: Часть URL, человекочитаемый идентификатор из букв, цифр, дефисов: `карандаш-простой-hb`. `SlugField` — поле для него. `allow_unicode=True` разрешает кириллицу, `db_index=True` создаёт индекс для быстрого поиска. Заполняется в админке автоматически (`prepopulated_fields`). **В итоговых маршрутах slug не используется** — адрес продукта строится по id.

**В: Что такое индекс в БД?**
О: Вспомогательная структура, ускоряющая поиск по столбцу — как алфавитный указатель в книге. Цена — замедление записи и место на диске.

**В: Зачем `get_absolute_url`?**
О: Метод модели, возвращающий канонический адрес страницы объекта. В шаблоне: `<a href="{{ product.product_price.get_absolute_url }}">`. Адрес формируется в одном месте через `reverse`; админка, найдя этот метод, показывает кнопку «View on site».

**В: Зачем `products/urls.py` и `include`?**
О: Маршруты приложения хранятся в самом приложении — проект делится на независимые части. В главном `urls.py`: `path('', include('products.urls'))`.

**В: Зачем `Price` и `Pozition_Price`? Почему цена не в `Product`?**
О: Цены меняются — утверждаются прайс-листами с номером и датой. `Price` — шапка прайса, `Pozition_Price` — строка: продукт и его цена. Так можно хранить историю цен. `auto_now_add=True` у даты — автоматически ставится дата создания записи.

**В: Почему `DecimalField` для цены?**
О: Точная десятичная арифметика без погрешностей `float`. `max_digits=7, decimal_places=2` — всего 7 цифр, из них 2 после запятой, максимум 99999.99.

**В: Что такое сессия?** *(главный вопрос ЛР 16–17)*
О: Механизм хранения данных конкретного посетителя между запросами. HTTP сам состояния не хранит. Работает так: при первой записи в `request.session` Django создаёт запись в таблице `django_session` и отправляет браузеру cookie `sessionid` со случайным ключом. При каждом следующем запросе браузер присылает cookie, `SessionMiddleware` по ключу загружает данные — они доступны как словарь `request.session`.

**В: Где физически хранятся данные сессии?**
О: На сервере, в таблице `django_session` (по умолчанию `SESSION_ENGINE = db`). Три столбца: `session_key` — ключ, `session_data` — данные (JSON, закодированный и подписанный `SECRET_KEY`), `expire_date` — срок действия. **В браузере — только ключ.** Срок жизни по умолчанию — 2 недели.

**В: Что нужно, чтобы сессии работали?**
О: `'django.contrib.sessions'` в `INSTALLED_APPS`, `SessionMiddleware` в `MIDDLEWARE` и применённые миграции. Всё есть по умолчанию. В методичке параметр назван `MIDDLEWARE_CLASSES` — это старое название, сейчас `MIDDLEWARE`.

**В: Cookie vs сессия?**
О: Cookie хранится у пользователя в браузере, он может её прочитать и изменить, размер ограничен ~4 КБ. Сессия хранится на сервере, пользователю недоступна; в cookie только идентификатор.

**В: Зачем `CART_SESSION_ID`?**
О: Имя ключа, под которым корзина лежит в сессии: `request.session['cart']`. Вынесено в настройки, чтобы не дублировать строку в коде.

## ЛР 17. Корзина

**Что сделано:** класс `Cart` в `cart/cart.py` → форма `CartAddProductForm` → представления `cart_add`, `cart_remove`, `cart_detail` → `cart/urls.py` → шаблон `cart/detail.html` → форма «Добавить в корзину» на странице продукта.

**Как корзина выглядит в сессии** (проверено):

```python
request.session['cart'] == {
    '1': {'quantity': 5, 'price': '25.00'},     # ключ — id позиции прайса (строкой)
}
```

**Класс `Cart` построчно:**

```python
class Cart(object):
    def __init__(self, request):
        self.session = request.session                     # запомнили сессию
        cart = self.session.get(settings.CART_SESSION_ID)  # пробуем достать корзину
        if not cart:
            cart = self.session[settings.CART_SESSION_ID] = {}   # нет — создаём пустую
        self.cart = cart

    def add(self, product, quantity=1, update_quantity=False):
        product_id = str(product.id)                       # ключ — строка
        if product_id not in self.cart:
            self.cart[product_id] = {'quantity': 0, 'price': str(product.cost_product)}
        if update_quantity:
            self.cart[product_id]['quantity'] = quantity   # заменить количество
        else:
            self.cart[product_id]['quantity'] += quantity  # прибавить
        self.save()

    def save(self):
        self.session[settings.CART_SESSION_ID] = self.cart
        self.session.modified = True                       # «сессия изменилась, сохрани»

    def remove(self, product):
        product_id = str(product.id)
        if product_id in self.cart:
            del self.cart[product_id]
            self.save()

    def __iter__(self):                                    # для {% for item in cart %}
        product_ids = self.cart.keys()
        productss = Pozition_Price.objects.filter(id__in=product_ids)   # один запрос на все
        for product in productss:
            self.cart[str(product.id)]['product'] = product
        for item in self.cart.values():
            item['price'] = Decimal(item['price'])
            item['total_price'] = item['price'] * item['quantity']
            yield item

    def __len__(self):                                     # общее количество штук
        return sum(item['quantity'] for item in self.cart.values())

    def get_total_price(self):                             # общая стоимость
        return sum(item['price'] * item['quantity'] for item in self.cart.values())

    def clear(self):
        del self.session[settings.CART_SESSION_ID]
        self.session.modified = True
```

**Вопросы:**

**В: Где хранится корзина?** *(спросят первым делом)*
О: В сессии пользователя под ключом `'cart'`, то есть на сервере в таблице `django_session`; в браузере только cookie `sessionid`. Отдельной модели/таблицы для корзины нет — `cart/models.py` пустой.

**В: Почему в сессии, а не в БД?**
О: Корзина — временные данные, должна работать и для гостей без регистрации, не требует миграций. Минусы: привязана к браузеру (с другого устройства корзина пустая), пропадает при истечении сессии или очистке cookie.

**В: Корзина работает для неавторизованных?**
О: Да. Сессия создаётся для любого посетителя, вход не нужен.

**В: Сохранится ли корзина после перезапуска сервера? Закрытия браузера? В другом браузере?**
О: После перезапуска сервера — да (данные в БД). После закрытия браузера — да, cookie живёт 2 недели. В другом браузере — нет, там другая cookie и другая сессия.

**В: Почему ключ — строка `str(product.id)`?**
О: Сессия сериализуется в **JSON**, а в JSON ключи объектов — только строки. Если положить число, после сохранения и загрузки оно станет строкой, и проверка `in` перестанет находить товар.

**В: Почему цена хранится строкой `str(product.cost_product)`?**
О: Цена — `Decimal`, а JSON не умеет сериализовать `Decimal` (ошибка «Object of type Decimal is not JSON serializable»). Сохраняем строкой, а при выводе превращаем обратно: `Decimal(item['price'])`.

**В: Зачем `self.session.modified = True`?**
О: Django сохраняет сессию, только если заметил изменение, а замечает он только присваивание по ключу верхнего уровня (`session['cart'] = ...`). Изменение вложенного словаря (`cart['1']['quantity'] += 1`) он не видит. Флаг говорит явно: «сохрани».

**В: Что делает `__iter__` и зачем?**
О: Позволяет писать `{% for item in cart %}`. В сессии только id, количество и цена, а для показа нужны название и картинка — метод одним запросом (`filter(id__in=...)`) достаёт объекты из БД, добавляет каждому элементу объект `product` и сумму по позиции `total_price`, и отдаёт элементы по одному через `yield`.

**В: Почему `filter(id__in=...)`, а не `get` в цикле?**
О: Один SQL-запрос (`WHERE id IN (1, 2, 3)`) вместо отдельного запроса на каждый товар.

**В: Что такое `yield`?**
О: Делает метод генератором: значения выдаются по одному по мере перебора.

**В: Что делает `@require_POST`?**
О: Декоратор: разрешает вызов представления только методом POST. На GET вернёт **405 Method Not Allowed**. Нужен, потому что добавление меняет данные.

**В: Что такое `TypedChoiceField` и `coerce=int`?**
О: Поле выбора из списка (`<select>`). Данные из формы всегда приходят строками; `coerce=int` приводит выбранное значение к целому — `'3'` → `3`, чтобы количество можно было складывать.

**В: Что будет, если отправить количество 30?**
О: 30 нет в списке `choices` (1–20) → `is_valid()` вернёт `False` → товар не добавится, произойдёт просто редирект в корзину. Проверено.

**В: Зачем скрытое поле `update`?**
О: Флаг режима: `False` — прибавить количество к имеющемуся, `True` — заменить. `HiddenInput` — пользователь его не видит. Пригодилось бы для изменения количества прямо в корзине; сейчас всегда `False`, поэтому повторное добавление суммируется (3 + 2 = 5).

**В: Что именно лежит в корзине — продукт или позиция прайса?**
О: **Позиция прайса** (`Pozition_Price`). Ключ корзины — её id, цена берётся из её `cost_product`. Название и картинка достаются через связь: `item.product.product_price.title`.

**В: Что произойдёт, если цена в прайсе изменится после добавления?**
О: В корзине останется старая — она сохранена в сессии в момент добавления.

**В: Что такое `{% with product=item.product %}`?**
О: Тег, создающий короткое имя для сложного выражения внутри блока.

**В: Как считается «Итого»?**
О: По позиции — `item.total_price` = цена × количество (в `__iter__`). Общее — `cart.get_total_price`: сумма по всем позициям.

**В: Что делает кнопка «Оформить заказ»?**
О: Ничего — ссылка-заглушка `href="#"`. Оформление заказа методичкой не предусмотрено. Для реализации нужны модели `Order` и `OrderItem`, форма, сохранение позиций в БД и `cart.clear()`.

**В: Где используется `clear()`?**
О: Пока нигде — заготовка для оформления заказа.

Это особенности кода — в основном унаследованные из методички (я сохранял её код и имена). На защите полезно показать, что ты их **видишь и понимаешь**. Формула ответа: *«так в методичке; я понимаю, что это значит; правильнее было бы так-то»*.

### 1. В модели `Product` два класса `Meta`

В `products/models.py` `class Meta` объявлен дважды. В Python второе определение **заменяет** первое. Итог (проверено): `ordering` пуст, индексов нет — первый `Meta` с `ordering = ['company']` и `index_together` полностью игнорируется.

- Заодно это спасает от ошибки: `index_together` **удалён в Django 5.1**; если бы первый `Meta` действовал, проект не запустился бы. Современная замена — `indexes = [models.Index(fields=['id', 'slug'])]`.
- Правильно — один `Meta` со всеми настройками.

### 2. `verbose_name = "Продукт",` — запятая в конце

Запятая превращает строку в **кортеж** `('Продукт',)`. Поэтому в админке при редактировании продукта название модели выглядит как `('Продукт',)` — это видно и в миграции 0008. Так на рисунке методички; исправление — убрать запятую и сделать миграцию.

### 3. Порядок маршрутов и дубли в `urls.py`

Django берёт **первое совпадение сверху вниз**:

- `path('', include('products.urls'))` стоит выше, поэтому `/product_list/` обрабатывается маршрутом из `products/urls.py`, а строка `re_path('product_list/', ...)` ниже в главном файле **никогда не срабатывает** (дубль из методички).
- `/detail_product/1` (без слэша) и `/detail_product/1/` (со слэшем) — **два разных маршрута и две разные страницы**: первый — `product_detail_1_view` из ЛР 9 (название и описание), второй — `product_detail` из ЛР 16–17 (картинка, цена, форма корзины).
- В `urlpatterns` три строки с `path('', ...)`: два `include` и главная. Конфликта нет: `include` с пустым префиксом просто добавляет маршруты приложения, а пустой путь `''` в них не определён.

### 4. `re_path` без якорей

`re_path('company_list/', ...)` — регулярное выражение без `^` и `$`, ищется как **подстрока**. Проверено: адрес `/xxcompany_list/yy` тоже открывает список компаний. Отсюда же важность порядка: `re_path('all_borrowed/', ...)` обязан стоять **выше** `re_path('borrowed/', ...)`, иначе `/all_borrowed/` попадал бы в «Мои заказы» (в нём есть подстрока `borrowed/`). Правильно: `path('company_list/', ...)` или `re_path(r'^company_list/$', ...)`.

### 5. Ссылки скрыты, а страницы — нет

`{% if user.is_superuser %}` прячет только пункт меню. По прямому адресу **без входа** открываются: `/detail/`, `/create/`, `/product_edit/<id>`, `/product_delete/<id>`, `/all_borrowed/` (проверено: код 200 для гостя). Защищена только `/borrowed/` — через `LoginRequiredMixin`.

Как правильно: `@login_required` / `LoginRequiredMixin` — требовать вход; `@user_passes_test(lambda u: u.is_superuser)`, `@staff_member_required`, `UserPassesTestMixin` или `@permission_required('products.delete_product')` — требовать права. **Скрытие в шаблоне — это удобство интерфейса, а не защита.**

### 6. Удаление по GET-ссылке

`/product_delete/<id>` и `/remove/<id>` меняют данные по обычной ссылке. Плохо: нет CSRF-защиты, нет подтверждения, ссылку может «нажать» поисковый робот или предзагрузка браузера. Правильно — форма с `method="post"`, `{% csrf_token %}` и `@require_POST`, как сделано для добавления в корзину.

### 7. `status_id__exact=2` и подписи на страницах

В БД: 1 — «На складе», 2 — «В заказе», 3 — «Продана». Код отбирает статус **2**, то есть «В заказе». Для «Моих заказов» и «Всех заказов» это логично. А на главной строка «Количество продуктов, доступных для заказа» на самом деле показывает число экземпляров **в заказе** — комментарий методички («На складе») не соответствует нашим id статусов.

Общая проблема — «магическое число»: код привязан к id записи в справочнике. Надёжнее `filter(status__name='В заказе')`.

### 8. `product_list` показывает весь прайс

Заголовок — «Продукция, которая есть в наличии на складе», но код — `Pozition_Price.objects.all()`: выводятся все позиции прайса без учёта статусов. Фильтр по статусу из ЛР 16 закомментирован (в ЛР 17 представление заменено на вариант с ценами).

### 9. `.get()` без обработки ошибок

- `/detail_product/9999` → `DoesNotExist` → ошибка 500 вместо 404. Лечится `get_object_or_404`.
- `product_detail` делает `Pozition_Price.objects.get(product_price_id=id)`: если продукта нет в прайсе — `DoesNotExist`; если он в двух прайс-листах — `MultipleObjectsReturned`. Сейчас прайс один, поэтому работает.

### 10. Корзина: тонкости

- **`{{ cart.len }}` в «Итого» пусто.** У `Cart` нет атрибута `len`, есть метод `__len__`. Шаблонизатор молча выводит пустоту для несуществующих атрибутов. Правильно: `{{ cart|length }}`.
- **`get_total_price` работает только после перебора корзины.** В сессии цена — строка; в `Decimal` её превращает `__iter__`. В шаблоне цикл `{% for %}` идёт раньше итога — поэтому всё считается. Если вызвать `get_total_price()` до перебора — `TypeError` (проверено). Надёжнее: `Decimal(item['price']) * item['quantity']`.
- **`__iter__` пишет объекты прямо в словарь сессии** (`Pozition_Price`, `Decimal`). Если бы сессия сохранялась в том же запросе — была бы ошибка сериализации JSON (проверено). На странице корзины сессия не меняется и не сохраняется, поэтому ошибки нет. Правильно — перебирать копию.
- **Картинка в корзине не кликабельна:** `product.get_absolute_url` вызывается у `Pozition_Price`, а метод есть только у `Product` → пустой `href`.
- **Опечатка в заглушке:** `{% static 'imges/no_image.png' %}`, а файл — `static/images/no_images.png`. Не проявляется: у всех товаров есть картинки. В `product_list.html` путь правильный.

- После успешного POST нет редиректа — F5 создаст дубль записи.
- Ошибки валидации не показываются: после проверки форма пересоздаётся пустой (`form = ProductForm()`). В браузере спасает HTML-атрибут `required`.

### 12. Форма редактирования

Сделана вручную на HTML, без формы Django: нет валидации, можно сохранить пустое название. Редирект `HttpResponseRedirect("/detail")` — без слэша, поэтому происходит лишний переход 301 на `/detail/` (`CommonMiddleware`, `APPEND_SLASH=True`).

### 14. Параметр `next` в ссылке «Вход»

`href="{% url 'login' %}? next="{{request.path}}"` — пробел после `?` и лишние кавычки ломают параметр. После входа пользователь попадает на `LOGIN_REDIRECT_URL` (`/`). Правильно: `href="{% url 'login' %}?next={{ request.path }}"`.

| `MIDDLEWARE_CLASSES` | так назван параметр | `MIDDLEWARE` | старое название, переименовано ещё в Django 1.10 |
| `index_together` | в `Meta` | написан, но не действует | удалён в Django 5.1; спасает второй `Meta` (часть 5, п. 1) |
| `context_processors.debug` | есть в `TEMPLATES` | нет | убран из шаблона проекта |
| Блок `MAILERS` | нет | есть в конце `settings.py` | добавляется `startproject` в Django 6.1 |
| Имена миграций | `0002_alter_product_description_...` | `0002_alter_product_options_..._and_more` | другой алгоритм именования |
| `manage.py shell` | модели импортируются вручную | пишет «objects imported automatically» | автоимпорт моделей с Django 5.2 |
| Язык интерфейса | русский | английский | `LANGUAGE_CODE='en-us'`; в методичке — автоперевод браузера |
| Номера строк `settings.py` | другие | — | файл другой версии |
| Вид админки | старый | новый, с переключателем темы | новая версия |
| SQLiteStudio | установщик с filehorse | портативная версия с официального GitHub | безопасный источник |
| Импорт `LoginRequiredMixin` | на рисунке не показан | добавлен | без него класс не работает |

Если спросят «почему не как в методичке» — ответ: *«код методички сохранён; отличия только там, где на актуальной версии Django он не работает, изменения минимальные»*.

| **DRY** | Don't Repeat Yourself — не дублировать код |
| **HTTP** | протокол обмена между браузером и сервером |
| **JSON** | текстовый формат данных; в нём хранится содержимое сессии |
| **Middleware** | промежуточный обработчик запросов и ответов |
| **MVT** | Model–View–Template, архитектура Django |
| **ORM** | объектно-реляционное отображение |
| **PK / FK** | первичный / внешний ключ |
| **PRG** | Post/Redirect/Get — редирект после обработки формы |
| **QuerySet** | ленивый набор объектов модели |
| **SQL** | язык запросов к реляционным БД |
| **Slug** | человекочитаемый идентификатор в URL |
| **WSGI / ASGI** | синхронный / асинхронный интерфейс сервер ↔ приложение |
| **XSS** | внедрение вредоносного скрипта на страницу |
| **Валидация** | проверка корректности данных |
| **Виджет** | способ отображения поля формы в HTML |
| **Контекст** | словарь данных для шаблона |
| **Контекстный процессор** | функция, добавляющая переменные во все шаблоны (`user`, `request`) |
